# 1.28.0 migration notes

## Protect GET /traefik-config with a bearer token (PAN-1885 / GHSA-jrw8)

No database change. Config change for operators.

`GET /api/v1/traefik-config` on the internal port returns every org's Traefik
config, including custom request header values and the gateway trust tokens.
It can now require a bearer token:

1. Generate a random value, for example `openssl rand -base64 32`.
2. Add it to `config/config.yml`:
   ```yaml
   traefik:
       config_token: "<value>"
   ```
3. Add the same value to Traefik's HTTP provider in
   `config/traefik/traefik_config.yml`:
   ```yaml
   providers:
     http:
       endpoint: "http://pangolin:3001/api/v1/traefik-config"
       pollInterval: "5s"
       headers:
         Authorization: "Bearer <value>"
   ```
4. Restart Pangolin and Traefik.

If `traefik.config_token` is not set, the endpoint keeps working without a
token and Pangolin logs a warning at the first request.

Deployments where Traefik does not poll this endpoint (`traefik.file_mode`,
or Traefik configured through Kubernetes CRDs, as on SaaS) can set
`traefik.disable_http_config: true` to turn it off entirely. New installs from the
installer get a token in both files automatically.

## Local sites (PAN-1885 / GHSA-jrw8)

No database change.

- `flags.disable_local_sites` and `flags.disable_basic_wireguard_sites` are now
  enforced by the API, not just hidden in the dashboard. `traefik.site_types`
  is not checked when creating a site, because remote exit nodes serve local
  sites even when the central Traefik does not.
- Targets on a `local` site that Pangolin's own Traefik serves (no exit node,
  or a Gerbil exit node) can no longer point at loopback, link-local
  (including `169.254.169.254`), `localhost`, `pangolin` (or the configured
  `server.internal_hostname`), `gerbil`, `traefik` or `badger`. Existing
  targets like that are skipped when the Traefik config is generated, so a
  resource that relied on one stops routing after the upgrade.
- Local sites on a **remote exit node** are not affected: that node's Traefik
  dials the targets inside the customer's network, where `localhost` targets
  are normal, and the hybrid Traefik config is generated as before.
- Find affected targets before upgrading:
  ```sql
  select r."orgId", r."resourceId", r."name", t."targetId", t."ip", t."port"
  from "targets" t
  join "resources" r on r."resourceId" = t."resourceId"
  join "sites" s on s."siteId" = t."siteId"
  left join "exitNodes" e on e."exitNodeId" = s."exitNode"
  where s."type" = 'local'
    and coalesce(e."type", '') <> 'remoteExitNode'
    and (t."ip" ~* '^(localhost|pangolin|gerbil|traefik|badger)$'
         or t."ip" like '127.%' or t."ip" like '169.254.%'
         or t."ip" in ('0.0.0.0', '::1', '::'));
  ```
- SaaS: keep local sites enabled (remote exit nodes use them). The central
  `traefik.site_types: ["newt"]` already keeps Pangolin's own Traefik from
  serving them.

## Outbound URL guard for AI providers, alert webhooks and log streaming (PAN-1799 / 3v9x, 4g5q)

No database change.

Tenant-supplied outbound URLs can no longer reach loopback, link-local
(including the cloud metadata service at `169.254.169.254`), multicast or
reserved addresses, `localhost`, `host.docker.internal`, or Pangolin's own
service names (`server.internal_hostname`, `gerbil`, `traefik`, `badger`). The
AI gateway re-checks the address it actually connects to on every request.
Alert webhooks and HTTP log streaming no longer follow redirects.

New flag `flags.block_private_outbound_urls` also refuses private networks
(RFC1918, IPv6 ULA, `100.64.0.0/10`). It defaults to `true` on SaaS and `false`
on self-hosted, where AI providers often point at local models.

Existing AI providers with a blocked upstream stop working after the upgrade
(the gateway returns an error). Find them first:
```sql
select "providerId", "orgId", "name", "upstreamUrl" from "aiProviders"
where "upstreamUrl" ~* '://(localhost|127\.|0\.|169\.254\.|\[|host\.docker\.internal|pangolin|gerbil|traefik|badger|metadata)';
```

## Domain bans in bannedEmails

No schema change. `bannedEmails` entries starting with `@` now ban a whole
domain and its subdomains (`@example.com` also matches `@mail.example.com`),
and `name+tag@domain` matches a ban on `name@domain`. The check applies to
signup and to new users provisioned through an OIDC IdP.
